## 前端预筛（按执行顺序）

### ① 强化下限 `enhanceLimit`

UI 是多选下拉 `optionsEnhanceLimit`，选 +0 / +3 / +6 … +15。选 +15 时只留满强化装备。

```javascript
// optimizerTab.js:L471-474
if (params.enhanceLimit) {
    const limit = params.enhanceLimit.length > 0 ? parseInt(params.enhanceLimit[0]) : 0;
    items = items.filter(x => x.enhance >= limit);
}
```

### ② 排除套装 `inputExcludeSet`

多选下拉 `inputExcludeSet`，被勾选的套装名（加 "Set" 后缀）全部排除。

### ③ 排除已穿上的装备 `excludeFilter`

多选下拉 `optionsExcludeGearFrom`（按英雄名列出）。被勾选英雄身上穿的装备排除 —— **当前英雄自己的不算**。

### ④ 套装硬约束 `inputSets`（仅 4+2 和 2+2+2 场景）

当选了特定的 4 件套 + 2 件套组合，或者 2+2+2 组合时，候选装备先筛到这些套装内。**普通"只选一个 4 件套"不走这条路**，普通场景的套装选择只影响 Top% 过滤里"选中套装 vs 其它套装"的名额分配。

```javascript
// optimizerTab.js:L486-493
const setConstrained = isFourAndTwoPieceSets(params.inputSets) || isTwoAndTwoAndTwoPieceSets(params.inputSets);
if (setConstrained) {
    const possibleSets = params.inputSets.flat();
    items = items.filter(x => possibleSets.includes(x.set));
}
```

### ⑤ 允许已装备 `inputAllowEquippedItems` & ⑥ 允许锁定 `inputAllowLockedItems`

两个复选框，☐ = 排除（当前英雄自己穿的仍保留），☑ = 全部纳入。

### ⑦ 英雄优先级 `inputOrderedHeroPriority`

复选框，☑ 时排在当前英雄前面的所有英雄身上装备全排除 —— 保证"按英雄顺序配装"时前面英雄已穿的装备不动。

### ⑧ 保留当前装备 `inputKeepCurrentItems`

复选框，☑ 时当前英雄已经穿的 6 件装备**从候选里排除**（强制换一套）。

### ⑨ 主属性过滤

三个独立的多选下拉：
- `inputNecklaceStat` — 项链主属性
- `inputRingStat` — 戒指主属性
- `inputBootsStat` — 靴子主属性

默认全选。只在 `x.gear == 'Necklace'` 时检查项链下拉，其它部位不受影响。

### ⑩ 预测重铸 `inputPredictReforges`

复选框。☑ 时把可重铸装备的 substat/main 值替换成重铸后的值（`Reforge.isReforgeableNow` 判断），再进入后续过滤。这会影响：
- 支配过滤里的属性比较值
- 属性优先级 score 计算
- 属性上下限判断（后端硬约束）

### ⑪ 子属性改造 `inputSubstatMods`

复选框，开启后 +15 装备会根据英雄的改造配置（keepStats / ignoreStats / discardStats / limitRolls / rollQuality / modGrade）生成改造版装备。

**关键行为：原版保留进候选**。每件装备先 `push` 原版，再为每个可改造的 substat × 每个 keep 目标生成改造版 `itemCopy`。原版和改造版同部位同套装进入后续过滤，score 高的胜出 —— 改造后不如改造前的装备自然会被淘汰。

```javascript
// modificationFilter.js:L86-L92, L209-L224
for (item of items) {
    newItems.push(item);          // 原版先入列（modId = 原 id）

    if (item.disableMods) continue;

    // ...生成改造版 itemCopy（modId = 新 uuidv4）...
    newItems.push(itemCopy);      // 改造版追加（如果条件满足）
}
return newItems;                  // 返回：原版 + 改造版合集
```

**改造生成条件**：
- 装备 `enhance == 15`
- substat rolls ≤ `limitRolls`，或 substat 已经 `modified`
- substat type 在 discardList / keepList 里，且不在 ignoreList 里
- 武器不能改防御、防具不能改攻击
- 目标 stat 不能和 main type 重复
- 如果已经有一个 substat 被改过（`substat.modified`），不再改另一个 substat
- 如果原来的 substat 值已经 ≥ 目标 roll 值（按 rollQuality 算出），不生成这件改造版

### ⑫ 支配过滤 `DominanceFilter.apply()`

**只在 `inputFilterPriority < 100` 时启用**（100 = 完全禁用）。

分组键：`部位 × 套装`（例如 `"Weapon\u0000AttackSet"`）。每组内两两比较，属性维度是 8 个基础属性：Attack / Health / Defense / Speed / CriticalHitChance / CriticalHitDamage / Effectiveness / EffectResistance。

**比较模式（getComparisonMode）由属性上下限 + resultDislike 决定**：

| 条件 | 比较模式 | 含义 |
|---|---|---|
| max 未设 & min 空 & 不 disliked | `higher` | 越高越好（默认） |
| max 未设 & min 空 & disliked | `lower` | 越低越好 |
| max 未设 & min > 0 & 不 disliked | `higher` | 高于下限就行，越高越好 |
| max 未设 & min > 0 & disliked | `equal` | 刚好等于下限最好（多了也不好） |
| max 未设 & min = 0 | `ignored` | 这个属性不参与支配判断 |
| max 设了 & min > 0 | `equal` | 卡区间，等于值最好 |
| max 设了 & min 空/0 & 不 disliked | `equal` | 卡区间 |
| max 设了 & min 空/0 & disliked | `lower` | 上限越低越好 |

支配定义：装备 A 在**所有**属性维度上 ≥ 装备 B，且**至少一个**维度严格 >，则 B 被淘汰。同值（所有维度 `equal`）的装备只留一件，胜者由 tiebreaker 决定：score 高 → 未加权 roll 总和大 → id 小。

### ⑬ Top% 优先级过滤 `PriorityFilter.apply()`

**只在 `inputFilterPriority < 100` 时启用**（100 表示完全禁用，所有候选进后端）。

执行顺序：
1. 用属性优先级滑块计算每件装备的 score（score 计算见下节）
2. 按 `部位 × 套装` 分组，每组按 score 降序排
3. 名额分配（分两类池）：
   - **用户选中的套装**：每个套装各自取 Top%，**件数下限 3**（`SELECTED_SET_MIN_KEEP`）
   - **其它套装**：把所有"没被选中的套装"合并成一个大池，一起排序后取 Top%
4. 同分时的 tiebreaker：resultPriority 字段顺序 → 未加权 roll 总和 → id

```javascript
// priorityFilter.js:L270-274（选中套装）
for (const group of slot.selected) {
    const quota = Math.max(SELECTED_SET_MIN_KEEP, quotaOf(group.total, percentage));
    // group.total = 全量装备里同部位同套装的件数（不是候选数）
}

// priorityFilter.js:L278-292（其它套装合并）
const merged = [];
for (const group of slot.others) for (const item of group.items) merged.push({ group, item });
merged.sort(compare);
// merged 里的所有 item 一起排，取前 quotaOf(slot.othersTotal, percentage) 件
```

**为什么 4+2 / 2+2+2 时只有第一条生效**：因为 ④ 套装硬约束先把候选筛成了用户选中的那几个套装，"其它套装"池是空的。

## 装备 score 计算（属性优先级滑块）

`attributePriority.js` 定义了 8 个滑块，默认全部 0（不参与评分）。滑块范围 0~8。

roll 的计算口径（统一公式）：

```
攻击 roll   = (攻击% + 主属性攻击% + (攻击值 + 主属性攻击值) / 基础攻击 × 100) / 8
生命 roll   = (生命% + 主属性生命% + (生命值 + 主属性生命值) / 基础生命 × 100) / 8
防御 roll   = (防御% + 主属性防御% + (防御值 + 主属性防御值) / 基础防御 × 100) / 8
速度 roll   = (速度值 + 主属性速度值) / 4
暴击率 roll = (暴击率% + 主属性暴击率%) / 5
暴击伤害 roll = (暴击伤害% + 主属性暴击伤害%) / 7
效果命中 roll = (效果命中% + 主属性效果命中%) / 8
效果抵抗 roll = (效果抵抗% + 主属性效果抵抗%) / 8

装备 score = Σ(属性 roll × 属性优先级权重)
```

主属性如果也是该属性，就加进去；否则为 0。百分比和数值属性按基础值归一化，这样攻击值 + 攻击% 的贡献能合并成一个可比数字。

## 后端硬约束（求解器剪枝）

所有上下限都是闭区间 `[min, max]`，后端用 `Configured` 布尔标记判断是否启用：`true` 表示前端真的填了值；`false` 表示前端留空或等于默认值（0 / Integer.MAX_VALUE），后端直接跳过该约束。

## resultPriority 怎么介入（完整分析）

`resultPriority` 不在 score 里，而是在**三个不同环节**分别起作用，且每个环节的介入方式和影响范围完全不同。resultDislike 是它的辅助字段：声明"这些字段越低越好"。

### 总览

```
装备 score（属性优先级滑块权重算的）
  │
  │  100 件候选
  │
  ├─ PriorityFilter.apply() —— Top% 过滤
  │   ├─ 主排序 key = score（不等就直接定）
  │   └─ 同分 tiebreaker = resultPriority（8 基础属性 × sign）+ unweightedRolls + id
  │       ↑ 只看 resultPriority 里那 8 个在 RESULT_STAT_KEYS 里的字段
  │       ↑ 派生属性 (ehp/dmg/s1~s3) 这阶段跳过
  │
  │  20 件进后端
  │
  ├─ DominanceFilter.apply() —— 支配淘汰
  │   ├─ 完全不看 score
  │   └─ 同组 pairwise 比较：每个维度"多少算好"由 resultDislike + 上下限决定
  │       ↑ 只看 resultDislike，不看 resultPriority 的 order
  │
  │  后端 solver 穷举 → 出 5000 条组合
  │
  ├─ TopKResultCollector.offer() —— 保留 Top 500
  │   ├─ 全字段覆盖（17 个，含派生属性）
  │   └─ 按 resultPriority 顺序逐字段比；disliked 字段反序
  │
  │  500 条返回前端，展示时按同一 comparator 排序
```

### 阶段 ①：PriorityFilter 的同分 tiebreaker

**时机**：属性优先级滑块算完 score 之后、Top% 名额分配之前。

**位置**：`priorityFilter.js:L83-L125` — `buildComparator`

**介入方式**：**只在 score 相同的时候才介入**，score 不等时直接出结果。

```javascript
// priorityFilter.js:L105-L124，候选排序比较器
return (left, right) => {
    if (left.score !== right.score) {
        return right.score - left.score;   // ← 先比 score，不等就直接定
    }
    // score 相等才往下走
    const a = tiebreak(left);
    const b = tiebreak(right);
    for (let i = 0; i < a.fields.length; i++) {     // ← resultPriority 按顺序比
        if (a.fields[i] !== b.fields[i]) {
            return a.fields[i] > b.fields[i] ? -1 : 1;
        }
    }
    if (a.rolls !== b.rolls) { ... }                 // ← 再比未加权 roll 总和
    return compareIds(left.id, right.id);            // ← 最后比 id
};
```

tiebreaker 数组怎么从 resultPriority 构出来：

```javascript
// priorityFilter.js:L84-L89
const fields = params.resultPriority
    .filter(field => RESULT_STAT_KEYS[field])       // 只保留 8 个可比较属性字段
    .map(field => ({
        key: RESULT_STAT_KEYS[field],               // atk→Attack, spd→Speed…
        sign: resultDislike.includes(field) ? -1 : 1 // disliked 字段乘 -1（越低越好）
    }));
```

**限制**：只有 `atk / hp / def / spd / cr / cd / eff / res` 这 8 个基础属性字段能进入 tiebreaker。`ehp / dmg / mcdmg / dmgh / dmgd / s1~s3 / score / bs / priority` 这些后端才有的派生属性在**前端候选阶段跳过** —— 候选阶段还没有完整结果行，算不出 EHP、DMG。

**例子**：resultPriority = `['cd', 'cr', 'spd']`，resultDislike = `['spd']`

| 比较字段 | 映射到装备属性 | sign | 含义 |
|---|---|---|---|
| `cd` | `CriticalHitDamagePercent` | +1 | 暴击伤害越高越好 |
| `cr` | `CriticalHitChancePercent` | +1 | 暴击率越高越好 |
| `spd` | `Speed` | **-1** | 速度鞋的速度越低越好 |

当两件装备 score 一样时，先比 CD（降序），CD 一样再比 CR，CR 一样再比 SP（**升序**），最后比未加权 roll 总和、比 id。

### 阶段 ②：DominanceFilter 的比较方向

**时机**：**完全不看 score**，在同一个"部位 × 套装"组内两两比较属性值，决定谁被谁支配。

**位置**：`dominanceFilter.js:L238-L277` — `getComparisonMode`

**介入方式**：**只看 resultDislike**，不看 resultPriority 的 order。它不决定"排序"，而是改变"支配关系的判准" —— 对 disliked 字段，它改变了"多大算好"的方向。

```javascript
// dominanceFilter.js:L269-L272
function isDislikedInResultPriority(params, definition) {
    return Array.isArray(params.resultDislike)
        && params.resultDislike.includes(definition.priorityField);
}
```

支配过滤的完整比较模式表（已在上文出现，这里对照 resultDislike 再强调一次）：

| 条件 | 比较模式 | 含义 | disliked 的改变 |
|---|---|---|---|
| max 未设 & min 空 & 不 disliked | `higher` | 越高越好 | — |
| max 未设 & min 空 & **disliked** | `lower` | 越低越好 | ← 默认的反方向 |
| max 未设 & min > 0 & 不 disliked | `higher` | 高于下限就行 | — |
| max 未设 & min > 0 & **disliked** | `equal` | 刚好等于下限最好 | ← 从 higher 变成 equal |
| max 未设 & min = 0 | `ignored` | 不参与判断 | — |
| max 设了 & min > 0 | `equal` | 卡区间 | — |
| max 设了 & min 空/0 & 不 disliked | `equal` | 卡区间 | — |
| max 设了 & min 空/0 & **disliked** | `lower` | 上限越低越好 | ← 从 equal 变成 lower |

**和 tiebreaker 的关键区别**：tiebreaker 是"先按 score 排，同分才看 resultPriority"；支配过滤**完全不看 score**，而是逐维度 pairwise —— 两件装备每个维度都要比一遍，只要 A 在**所有**维度上 ≥ B 且至少一个严格 >，B 就淘汰。resultDislike 改变的是每个维度"多少才算 ≥"。

**例子**：速度鞋，resultDislike 包含 `spd`，没设速度上限

| 模式 | 含义 | 速度鞋比较口径 |
|---|---|---|
| `higher`（默认，不 disliked） | 速度高的"好" | `(A.spd > B.spd) → A 在速度维支配 B` |
| `lower`（disliked + 没设上限） | 速度低的"好" | `(A.spd < B.spd) → A 在速度维支配 B` |
| `equal`（disliked + 设了 min > 0） | 刚好等于下限"最好" | 偏离 min 越远越差 |

### 阶段 ③：后端 Top-K 保留 + 结果排序

**时机**：穷举 6 件组合、计算完整结果行、过属性上下限约束之后。

**位置**：`TopKResultCollector.java` + `ResultPriorityComparator.java`

**介入方式**：**主力排序 key**，覆盖全部 17 个字段（`resultPriority.js` 里的 `RESULT_PRIORITY_FIELDS`），包括前端算不出来的派生属性：

```java
// ResultPriorityComparator.valueOf —— switch 映射全字段
case "atk":    return stats.getAtk();
case "ehp":    return stats.getEhp();    // 派生：HP × (1 + DEF/200)
case "dmg":    return stats.getDmg();    // 派生：单技能伤害估算
case "mcdmg":  return stats.getMcdmg();  // 派生：暴击伤害
case "dmgh":   return stats.getDmgh();   // 派生：持伤
case "dmgd":   return stats.getDmgd();   // 派生：防御贡献伤害
case "s1":     return stats.getS1();     // S1 专属装备件数

```

**为什么这阶段能用派生属性而前端不行**：TopKResultCollector 接收的 `HeroStats` 已经是完整结果行 —— solver 已经对 6 件装备算完了英雄属性、EHP、DMG、S1~S3 件数这些。前端候选阶段只看单件装备，没有完整英雄上下文。

Top-K 保留器的 comparator：

```java
// TopKResultCollector.java:L54
// heap 里最小的"最差结果"在 head，新结果更好就顶掉它
public synchronized void offer(final HeroStats result) {
    if (heap.size() < capacity) { heap.offer(result); return; }
    if (bestFirstComparator.compare(result, heap.peek()) < 0) { // result 更好
        heap.poll();
        heap.offer(result);
    }
}
```

bestFirstComparator（就是 ResultPriorityComparator）：

```java
// ResultPriorityComparator.compare
public int compare(final HeroStats left, final HeroStats right) {
    for (final String field : orderedFields) {        // ← 按 resultPriority 顺序
        final int cmp = dislikedFields.contains(field)
                ? Integer.compare(valueOf(right, field), valueOf(left, field))  // disliked → 反序（越低越好）
                : Integer.compare(valueOf(left, field), valueOf(right, field)); // 正常 → 正序（越高越好）
        if (cmp != 0) return -cmp;                    // 不等直接出结果
    }
    // resultPriority 全比完都相等 → 用这些兜底
    if (left.priority != right.priority) return -cmp(priority);
    if (left.bs       != right.bs)       return -cmp(bs);
    if (left.score    != right.score)    return -cmp(score);
    return -cmp(dmg);
}
```

Top-K 的容量是 `MAX_RETAINED_RESULTS = 500`。heap 先积累满 500 条，之后每来一条就跟 head（当前最差）比，resultPriority 判定更好就顶掉旧的。最终输出时再按 comparator 排序一遍得到 best-first 顺序。

### 三个阶段的介入方式汇总

| 阶段 | 比较对象 | resultPriority 介入方式 | 影响范围 | resultPriority 覆盖字段 |
|---|---|---|---|---|
| PriorityFilter tiebreaker | 单件装备的 score + 同部位同套装其它单件 | **只在 score 相同**时逐字段比（8 基础属性） | 候选装备数量（减少进后端的件数） | 8 基础属性（atk/hp/def/spd/cr/cd/eff/res） |
| DominanceFilter 比较方向 | 单件装备 vs 同组内其它单件的逐维度支配关系 | **只看 resultDislike** 改变比较方向（higher/lower/equal/ignored） | 候选装备数量（淘汰被支配装备） | 8 基础属性（和上下限一起决定） |
| TopKResultCollector | **完整结果行**（6 件装备 × 算完属性 × 派生属性都有） | **主力排序**：resultPriority 顺序逐字段比，disliked 反序 | Top-K 留哪 K 条 + 最终展示顺序 | 17 字段全覆盖（8 基础 + ehp/dmg/mcdmg/dmgh/dmgd/s1~s3/score/bs/priority） |

## 子属性改造的 keep/ignore/discard 三列表

| 列表 | 含义 |
