## 属性计算链路（bonus 分层 + 取整规则）

### 游戏取整规则（已验证）

**6 件装备合计后统一 floor**，不是每件装备单独 floor。公式：

```
最终面板 atk = floor( (bonusBaseAtk + Σ装备贡献 + setBonus) × bonusMaxAtk )
```

验证数据（指挥官萝里娜，bonusMaxAtk=1.0，无 final multiplier，无神器）：

```
herodata.json Commander Lorina lv60: atk = 1313（技能树 20% 已在 base 里）
装备 = 32% atk + 52 flat atk

游戏面板: 1313 + floor(52 + 1313 × 32/100) = 1313 + floor(472.16) = 1313 + 472 = 1785 ✅
代码结果: 同公式一致 ✅
```

`floor(a) + floor(b) + floor(c) ≠ floor(a + b + c)`，差异范围 `[1, N-1]`（N = 加数个数）。因此 **accumulator 不能提前 floor**，必须保留 float 加完 6 件再统一 floor（bonusMaxAtk 乘完后）。

### bonus 分层（两层）

| 层 | 名称 | 位置 | 公式 | 来源 |
|---|---|---|---|---|
| **加法层** | bonusBaseAtk | 括号里直接加 | `base.atk × (1 + heroBonusAtkPercent/100) + heroBonusAtk + aeiAtk` | 技能树 flat + 神器 flat + 英雄自带 percent bonus |
| **乘法层** | bonusMaxAtk | 括号外面乘 | `1 + bonusMaxAtkPercent/100 + finalAtkMultiplier/100` | 英雄自带 final multiplier（如 Aki S3）+ 用户手动填的 Final Attack |

**自阵**（overrideAtk）走加法层——直接覆盖 `hero.atk`（base 本身被换掉），**不走** bonusMaxAtk 乘法。所以自阵和装备 percent 是同级加法，不会互相放大。

bonusMaxAtkPercent 来自 `herodata.json` 的 `calculatedStatus`（不是自阵），是英雄自带的被动 final multiplier（如 Aki 有 50%，萝里娜没有）。

### accumulator 设计

**每件装备单独生成 accumulator**，存进 `float[15]`：

```java
// StatCalculator.buildStatAccumulatorArr
statAccumulatorArr[0] = stats.getAttack() + stats.getAttackPercent()/100f * base.getAtk();  // atk
statAccumulatorArr[1] = stats.getHealth() + stats.getHealthPercent()/100f * base.getHp();    // hp
statAccumulatorArr[2] = stats.getDefense() + stats.getDefensePercent()/100f * base.getDef();  // def
statAccumulatorArr[6] = stats.getCritRate();         // cr（flat 整数）
statAccumulatorArr[7] = stats.getCritDamage();       // cd
statAccumulatorArr[8] = stats.getEffectiveness();    // eff
statAccumulatorArr[9] = stats.getEffectResistance();  // res
statAccumulatorArr[10] = stats.getSpeed();            // spd（flat 整数）
statAccumulatorArr[11] = score;                       // 综合评分（不是面板属性）
statAccumulatorArr[12] = set.index;                    // 套装编号
```

**为什么 accumulator 保留 float（不提前 floor）**：percent 转绝对值时有小数（`base.atk × 32 / 100` 可能 = 420.16）。6 件加完再 floor = 游戏行为。提前 floor 每件 → 最多差 5 点 atk。

### set bonus（完整列表）

| set index | 触发条件 | 奖励 | 作用属性 |
|---|---|---|---|
| 0 (生命) | > 1 件，每件 +38% HP | hpSetBonus = 0.38 × base.hp | hp |
| 1 (防御) | > 1 件，每件 +44% DEF | defSetBonus = 0.44 × base.def | def |
| 2 (暴击攻击) | > 3 件 | atkSetBonus = 0.45 × base.atk | atk |
| 3 (速度) | > 3 件 | speedSetBonus = 25 | spd |
| 4 (暴击率) | > 1 件，每件 +12 | — | cr |
| 5 (效果命中) | > 1 件，每件 +20 | — | eff |
| 6 (暴击伤害) | > 3 件，+60 | — | cd |
| 9 (效果抵抗) | > 1 件，每件 +20 | — | res |
| 14 (复仇) | > 3 件 | revengeSetBonus = 8 | spd |
| 17 (激流) | > 1 件，每件 HP/−2（带负号） | hpSetBonus / -2 | hp |
| 18 (反击) | > 3 件 | reversalSetBonus = 6 | spd |
| 20 (生命/速度) | > 3 件，+38% HP | hpSetBonus = 0.38 × base.hp | hp |
| 22 (速度/抗性) | > 3 件 | reversalSetBonus = 6 | spd |

### 最终面板公式（addAccumulatorArrsToHero）

```java
// atk/hp/def: bonusMax 乘在外面
final int atk = (int) ((bonusBaseAtk + Σ6件accumulator[0] + setBonus) * bonusMaxAtk);

// spd/cr/cd/eff/res: 无 bonusMax 乘法层
final int cr  = (int) (baseCr + Σ6件accumulator[6] + crSetBonus + bonusCr + aeiCr);
final int spd = (int) (baseSpd + Σ6件accumulator[10] + spdSetBonus + bonusSpd + aeiSpd);
```

## 前端预筛（按执行顺序）

### ① 强化下限 `enhanceLimit`

UI 是多选下拉 `optionsEnhanceLimit`，选 +0 / +3 / +6 … +15。选 +15 时只留满强化装备。

```javascript
// optimizerTab.js:L471-474
if (params.enhanceLimit) {
    const limit = params.enhanceLimit.length > 0 ? parseInt(params.enhanceLimit[0]) : 0;
    items = items.filter(x => x.enhance >= limit);
}
```

### ② 排除套装 `inputExcludeSet`

多选下拉 `inputExcludeSet`，被勾选的套装名（加 "Set" 后缀）全部排除。

### ③ 排除已穿上的装备 `excludeFilter`

多选下拉 `optionsExcludeGearFrom`（按英雄名列出）。被勾选英雄身上穿的装备排除 —— **当前英雄自己的不算**。

### ④ 套装硬约束 `inputSets`（仅 4+2 和 2+2+2 场景）

当选了特定的 4 件套 + 2 件套组合，或者 2+2+2 组合时，候选装备先筛到这些套装内。**普通"只选一个 4 件套"不走这条路**，普通场景的套装选择只影响 Top% 过滤里"选中套装 vs 其它套装"的名额分配。

```javascript
// optimizerTab.js:L486-493
const setConstrained = isFourAndTwoPieceSets(params.inputSets) || isTwoAndTwoAndTwoPieceSets(params.inputSets);
if (setConstrained) {
    const possibleSets = params.inputSets.flat();
    items = items.filter(x => possibleSets.includes(x.set));
}
```

### ⑤ 允许已装备 `inputAllowEquippedItems` & ⑥ 允许锁定 `inputAllowLockedItems`

两个复选框，☐ = 排除（当前英雄自己穿的仍保留），☑ = 全部纳入。

### ⑦ 英雄优先级 `inputOrderedHeroPriority`

复选框，☑ 时排在当前英雄前面的所有英雄身上装备全排除 —— 保证"按英雄顺序配装"时前面英雄已穿的装备不动。

### ⑧ 保留当前装备 `inputKeepCurrentItems`

复选框，☑ 时当前英雄已经穿的 6 件装备**从候选里排除**（强制换一套）。

### ⑨ 主属性过滤

三个独立的多选下拉：
- `inputNecklaceStat` — 项链主属性
- `inputRingStat` — 戒指主属性
- `inputBootsStat` — 靴子主属性

默认全选。只在 `x.gear == 'Necklace'` 时检查项链下拉，其它部位不受影响。

### ⑩ 预测重铸 `inputPredictReforges`

复选框。☑ 时把可重铸装备的 substat/main 值替换成重铸后的值（`Reforge.isReforgeableNow` 判断），再进入后续过滤。这会影响：
- 支配过滤里的属性比较值
- 属性优先级 score 计算
- 属性上下限判断（后端硬约束）

### ⑪ 子属性改造 `inputSubstatMods`

复选框，开启后 +15 装备会根据英雄的改造配置（keepStats / ignoreStats / discardStats / limitRolls / rollQuality / modGrade）生成改造版装备。

**关键行为：原版保留进候选**。每件装备先 `push` 原版，再为每个可改造的 substat × 每个 keep 目标生成改造版 `itemCopy`。原版和改造版同部位同套装进入后续过滤，score 高的胜出 —— 改造后不如改造前的装备自然会被淘汰。

```javascript
// modificationFilter.js:L86-L92, L209-L224
for (item of items) {
    newItems.push(item);          // 原版先入列（modId = 原 id）

    if (item.disableMods) continue;

    // ...生成改造版 itemCopy（modId = 新 uuidv4）...
    newItems.push(itemCopy);      // 改造版追加（如果条件满足）
}
return newItems;                  // 返回：原版 + 改造版合集
```

**改造生成条件**：
- 装备 `enhance == 15`
- substat rolls ≤ `limitRolls`，或 substat 已经 `modified`
- substat type 在 discardList / keepList 里，且不在 ignoreList 里
- 武器不能改防御、防具不能改攻击
- 目标 stat 不能和 main type 重复
- 如果已经有一个 substat 被改过（`substat.modified`），不再改另一个 substat
- 如果原来的 substat 值已经 ≥ 目标 roll 值（按 rollQuality 算出），不生成这件改造版

### ⑫ 支配过滤 `DominanceFilter.apply()`

**只在 `inputFilterPriority < 100` 时启用**（100 = 完全禁用）。

分组键：`部位 × 套装`（例如 `"Weapon\u0000AttackSet"`）。每组内两两比较，属性维度是 8 个基础属性：Attack / Health / Defense / Speed / CriticalHitChance / CriticalHitDamage / Effectiveness / EffectResistance。

**比较模式（getComparisonMode）由属性上下限 + resultDislike 决定**：

| 条件 | 比较模式 | 含义 |
|---|---|---|
| max 未设 & min 空 & 不 disliked | `higher` | 越高越好（默认） |
| max 未设 & min 空 & disliked | `lower` | 越低越好 |
| max 未设 & min > 0 & 不 disliked | `higher` | 高于下限就行，越高越好 |
| max 未设 & min > 0 & disliked | `equal` | 刚好等于下限最好（多了也不好） |
| max 未设 & min = 0 | `ignored` | 这个属性不参与支配判断 |
| max 设了 & min > 0 | `equal` | 卡区间，等于值最好 |
| max 设了 & min 空/0 & 不 disliked | `equal` | 卡区间 |
| max 设了 & min 空/0 & disliked | `lower` | 上限越低越好 |

支配定义：装备 A 在**所有**属性维度上 ≥ 装备 B，且**至少一个**维度严格 >，则 B 被淘汰。同值（所有维度 `equal`）的装备只留一件，胜者由 tiebreaker 决定：score 高 → 未加权 roll 总和大 → id 小。

### ⑬ Top K 候选过滤 `PriorityFilter.apply()`

**DominanceFilter 之后执行**，是后端穷举前的最后一道剪枝。滑块范围 10~50，默认 25，步长 5（K = 每个部位最多保留多少件）。

执行顺序：
1. 用属性优先级滑块计算每件装备的 score（score 计算见下节）
2. 按 `部位 × 套装` 分组，每组按 score 降序排
3. **按 Dominance 后实际件数占比分配 quota**（不再按主观权重）
4. 同分时的 tiebreaker：属性优先级滑块数值降序分桶比（同权重属性合并求和）→ disliked 属性兜底（越低越好）→ 未加权 roll 总和 → id

#### 未选池动态比例

选中套装数量决定未选池 quota 上限（意图越明确，未选话语权越小）：

| 选中套装数 | 未选池上限 | 典型场景 |
|---|---|---|
| 1 | 20% | 纯 4 件套（暴击攻击单独一组） |
| 2 | 15% | 4+2 / 2+2（两个套装组） |
| 3 | 10% | 2+2+2 |
| 4+ | 5% | 极多套装 |

```javascript
// priorityFilter.js:L95-L97
const OTHERS_MAX_RATIO_BASE = 0.20;   // 基础值（选中 1 套）
const OTHERS_MAX_RATIO_STEP = 0.05;   // 每多选中 1 套降 5%
const OTHERS_MAX_RATIO_MIN  = 0.05;   // 最低 5%
```

#### quota 分配规则（核心）

对**每个部位独立处理**：

```javascript
// 选中套装合计可用 = K × (1 - 未选上限)
const maxForSelected = Math.round(K * (1 - othersMaxRatio));
```

**选中套装之间**（精确合计 = maxForSelected，不超不欠）：
```
第 1 ~ N-1 个套装：quota = floor(maxForSelected × 该套装件数 / 选中总件数)
第 N 个套装（尾套装）：quota = maxForSelected - 前面所有套装 quota 之和  // 吃剩余，精确补齐

// floor 分配后每个 quota ≥ SELECTED_SET_MIN_KEEP(3) → 不用额外处理
// 如果 floor 后某个 quota < minKeep，先全部拉到 minKeep，
// 超出的部分从 quota 最大的套装依次扣减
```

**未选中套装**（合并成一个池）：
```
othersQuota = round(K × 未选 Dominance 后总件数 / 该部位总件数)
othersQuota = max(1, min(othersQuota, round(K × othersMaxRatio)))  // 1 保底 + 动态上限
```

#### spare 两轮 rebalance

第一轮每个套装按初始 quota 取前 N 件后，`spare = Σ max(0, quota - 该套装实际件数)`（实际不足 quota 的差额）。

第二轮按优先级补：
```
spare → 先补选中套装剩余候选（score 降序，哪个选中套装还有件就补哪）
      → 选中套装补完还有剩 → 补未选池剩余候选
```

K 是该部位**上限**，不是保证值 —— 如果 Dominance 后该部位总共就 N 件（N<K），实际就是 N 件。floor + 尾套装吃剩余保证选中套装 quota 合计精确等于 maxForSelected，不出现 round 误差导致的 quota 蒸发。

#### 完整数字推演（武器部位，K=25，4+2，选中 2 套 → othersMaxRatio=0.15）

| 套装 | 是否选中 | Dominance 后 | 占比 | 初始 quota | 实际保留 |
|---|---|---|---|---|---|
| 暴击攻击（4件） | ✅ | 12 | 86% | floor(21 × 12/14) = 18 | min(18, 12) = 12 |
| 生命（2件） | ✅ | 2 | 14% | 21 - 18 = 3（尾套装吃剩余） | min(3, 2) = 2 |
| 未选合并池 | ❌ | 6 | — | min(round(25×6/20), round(25×0.15)) = min(8, 4) = 4 | min(4, 6) = 4 |
| **合计** | | **20** | | | **18 + spare 2 件 rebalance → 20** |

spare = (18-12) + (3-2) = 7，但选中套装补完后剩余候选只有 0（暴击攻击 12 件全用完了、生命 2 件全用完了），所以 7 件 spare 里的 6 件补到未选池（未选池还有 6-4=2 件剩余），最终 12+2+6 = **20 件**（该部位 Dominance 后实际最大值）。

#### tiebreaker 详细逻辑

score 相等时，按**属性优先级滑块值降序**分桶，同权重的属性**合并成一个 sum 维度**（无需人为设同权重时的顺序）：

```
攻击=8, 暴率=3, 生命=3, 抗性=4, 速度 disliked（权重 0）

正权重桶（按滑块值降序，桶内加原始属性值，不做 dislike 处理）：
  权重 8: [攻击]      → sums[0] = 攻击值（高好）
  权重 4: [抗性]      → sums[1] = 抗性值（高好）
  权重 3: [暴率+生命] → sums[2] = 暴率 + 生命（高好）

disliked 兜底（全桶相等后才比，所有被标记 dislike 的属性 × sign=-1 求和）：
  速度（sign=-1）    → dislikedSum = -速度（高好 ← 实际是速度低的赢）

tiebreaker 顺序：sums[0] → sums[1] → sums[2] → dislikedSum → rolls → id
```

## 装备 score 计算（属性优先级滑块）

`attributePriority.js` 定义了 8 个滑块，默认全部 0（不参与评分）。滑块范围 0~8。

roll 的计算口径（统一公式）：

```
攻击 roll   = (攻击% + 主属性攻击% + (攻击值 + 主属性攻击值) / 基础攻击 × 100) / 8
生命 roll   = (生命% + 主属性生命% + (生命值 + 主属性生命值) / 基础生命 × 100) / 8
防御 roll   = (防御% + 主属性防御% + (防御值 + 主属性防御值) / 基础防御 × 100) / 8
速度 roll   = (速度值 + 主属性速度值) / 4
暴击率 roll = (暴击率% + 主属性暴击率%) / 5
暴击伤害 roll = (暴击伤害% + 主属性暴击伤害%) / 7
效果命中 roll = (效果命中% + 主属性效果命中%) / 8
效果抵抗 roll = (效果抵抗% + 主属性效果抵抗%) / 8

装备 score = Σ(属性 roll × 属性优先级权重)
```

主属性如果也是该属性，就加进去；否则为 0。百分比和数值属性按基础值归一化，这样攻击值 + 攻击% 的贡献能合并成一个可比数字。

### GPU / CPU 两层 stats filter（2026-11-15 重写）

8 项面板 stats filter 现在在两个地方都会执行——GPU kernel 里提前剪枝 + CPU 侧精确复判兜底。

**为什么两层**：GPU 在穷举时能并行砍掉大量明显不达标的组合（典型配装器用 4+2 套装，set filter 砍 ~30%，stats filter 再砍 ~80%，叠加后 GPU 层砍 ~86%），CPU executor 只处理真正有竞争力的组合。

#### GPU kernel 里的 filter

**set filter（阶段 1，GpuOptimizerKernel）**：纯整数查表，零 float，结果确定：

```
setIndex = weapon.set × 7962624 + helmet.set × 331776 + armor.set × 13824 + necklace.set × 576 + ring.set × 24 + boots.set
passes[id] = boolArr[setIndex]    // boolArr 是 25-bit 套装组合的合法判定表
```

SetFormat000OptimizerKernel（select format = 0 时）没有套装约束，跳过这一步。

**stats filter（阶段 2，两个 kernel 都做）**：accumulator 保留 float（不能提前 floor，见上文"取整规则"），GPU float 加法链与 Java 一致，最终 `(int)` floor 后和 `inputXxxMinLimit`/`inputXxxMaxLimit` 比较：

```java
// 伪代码（kernel run() 里）
final float atkSum = wAtk + hAtk + aAtk + nAtk + rAtk + bAtk;  // 6 件 accumulator float 汇总
final int finalAtk = (int) ((bonusBaseAtk + atkSum + atkSetB) * bonusMaxAtk);  // 完整公式 + floor
passes[id] = finalAtk >= inputAtkMinLimit && finalAtk <= inputAtkMaxLimit
           && finalHp  >= inputHpMinLimit  && finalHp  <= inputHpMaxLimit
           ...  // 8 项全比
```

所有 `bonusBaseAtk` / `bonusMaxAtk` / `baseCr` / `bonusCr` / `inputXxxLimit` / set bonus 参数都是构造函数里传进 kernel 的 `@Constant` 常量，不依赖 OpenCL float 编译选项（Aparapi 默认不用 `-cl-fast-relaxed-math`）。

#### CPU 侧的 passesUpdatedFilter（兜底复判）

在 `OptimizationRequestHandler` executor 的 for 循环里，对每条 `passes[id]=true` 的组合：

```java
HeroStats result = StatCalculator.addAccumulatorArrsToHero(...);  // 完整算 HeroStats
if (!passesUpdatedFilter(result, request)) continue;              // CPU 精确复判
resultCollector.offer(result);                                    // 过了才进 Top K
```

**为什么还要 CPU 复判**：GPU kernel 里用了简化的 set bonus 计数（kernel run() 里写死了 set index 条件），而 CPU 侧 `addAccumulatorArrsToHero` 用 `sets[index]` 数组查表——两者公式必须完全一致。如果以后加新套装漏改 kernel，CPU 复判能兜底。另外 GPU 不检查派生属性（dmg/cp/s1-s3/score/bs/priority 等），这些只在 CPU 侧过。

#### 稳定性保证（对比 2026-11-14 前的状态）

| 问题 | 之前（GPU 做 float stats filter） | 现在 |
|---|---|---|
| 结果漂移 | OpenCL float（-cl-fast-relaxed-math）和 Java float 精度不一致，边界 build 被误跳过 → 每次运行结果数不同 | GPU stats filter 也用完整公式，且**不使用** `-cl-fast-relaxed-math`，GPU/CPU 公式 100% 一致 |
| set filter 漂移 | 整数查表，不会漂 | 不变 |
| Top K 结果不稳定 | passes 数量每次不同，PriorityQueue 里比较时出现 0 返回 | ResultPriorityComparator 加 compareItems 兜底（装备 id 字典序大优先） |

## resultPriority 怎么介入（完整分析）

`resultPriority` 不在 score 里，而是在**三个不同环节**分别起作用，且每个环节的介入方式和影响范围完全不同。resultDislike 是它的辅助字段：声明"这些字段越低越好"。

### 总览

```
装备 score（属性优先级滑块权重算的）
  │
  │  100 件候选
  │
  ├─ PriorityFilter.apply() —— Top K 过滤
  │   ├─ 主排序 key = score（不等就直接定）
  │   └─ 同分 tiebreaker = 属性优先级滑块权重降序分桶比（同权重属性合并求和）
  │                        → disliked 属性兜底 → unweightedRolls → id
  │
  │  20 件进后端
  │
  ├─ DominanceFilter.apply() —— 支配淘汰
  │   ├─ 完全不看 score
  │   └─ 同组 pairwise 比较：每个维度"多少算好"由 resultDislike + 上下限决定
  │       ↑ 只看 resultDislike，不看 resultPriority 的 order
  │
  │  后端 solver 穷举 → 出 5000 条组合
  │
  ├─ TopKResultCollector.offer() —— 保留 Top 500
  │   ├─ 全字段覆盖（17 个，含派生属性）
  │   └─ 按 resultPriority 顺序逐字段比；disliked 字段反序
  │
  │  500 条返回前端，展示时按同一 comparator 排序
```

### 阶段 ①：PriorityFilter 的同分 tiebreaker

**时机**：属性优先级滑块算完 score 之后、Top K 名额分配之前。

**位置**：`priorityFilter.js` — `buildComparator`

**介入方式**：**只在 score 相同的时候才介入**。注意：tiebreaker 已经**不再使用 resultPriority**，而是用**属性优先级滑块数值**分桶（滑块数值就是权重）。resultPriority 的作用域现在只剩阶段 ② 和阶段 ③。

```javascript
// priorityFilter.js:L102-L110
// 8 个属性固定顺序（用于权重相同时的默认顺序，实际不单独判断）
const DEFAULT_TIEBREAKER_ORDER = [spd, hp, def, atk, cr, cd, res, eff];

// 从 params 读属性优先级滑块值，权重 > 0 的才进桶
const weightedFields = DEFAULT_TIEBREAKER_ORDER
    .map(e => ({ field, key, weight: params[inputXxxPriority] || 0 }))
    .filter(f => f.weight > 0)
    .sort((a, b) => b.weight - a.weight);  // 权重降序
```

tiebreaker 完整决策链：
```
score 不等 → 直接出结果（不进 tiebreaker）
score 相等：
  ① 正权重桶（滑块值降序，桶内加原始属性值）
     权重 8: [攻击]        → sums[0] = 攻击值（高好）
     权重 4: [抗性]        → sums[1] = 抗性值（高好）
     权重 3: [暴率, 生命]  → sums[2] = 暴率 + 生命（同权重合并求和）
  ② disliked 属性兜底（全桶相等后才比）
     所有被标记 dislike 的属性 × sign=-1 求和 → 越低越好
  ③ unweightedRolls（总 roll 多的好）
  ④ id（字符串比，必然不同除非同一件）
```

**和 resultPriority 的关系**：resultPriority 在前端 PriorityFilter 阶段**不参与 tiebreaker 排序**。resultDisliked 仍在 disliked 兜底和 DominanceFilter 比较方向里使用。

**限制**：同桶内不做 dislike 处理 —— 桶内加的是原始属性值，dislike 只在全桶相等后才单独兜底。这样 disliked 属性如果滑块权重 > 0，它的方向在桶里是"高好"，只有全桶都相等时才会被 disliked sign 翻成"低好"。两种方向都覆盖到了。

### 阶段 ②：DominanceFilter 的比较方向

**时机**：**完全不看 score**，在同一个"部位 × 套装"组内两两比较属性值，决定谁被谁支配。

**位置**：`dominanceFilter.js:L238-L277` — `getComparisonMode`

**介入方式**：**只看 resultDislike**，不看 resultPriority 的 order。它不决定"排序"，而是改变"支配关系的判准" —— 对 disliked 字段，它改变了"多大算好"的方向。

```javascript
// dominanceFilter.js:L269-L272
function isDislikedInResultPriority(params, definition) {
    return Array.isArray(params.resultDislike)
        && params.resultDislike.includes(definition.priorityField);
}
```

支配过滤的完整比较模式表（已在上文出现，这里对照 resultDislike 再强调一次）：

| 条件 | 比较模式 | 含义 | disliked 的改变 |
|---|---|---|---|
| max 未设 & min 空 & 不 disliked | `higher` | 越高越好 | — |
| max 未设 & min 空 & **disliked** | `lower` | 越低越好 | ← 默认的反方向 |
| max 未设 & min > 0 & 不 disliked | `higher` | 高于下限就行 | — |
| max 未设 & min > 0 & **disliked** | `equal` | 刚好等于下限最好 | ← 从 higher 变成 equal |
| max 未设 & min = 0 | `ignored` | 不参与判断 | — |
| max 设了 & min > 0 | `equal` | 卡区间 | — |
| max 设了 & min 空/0 & 不 disliked | `equal` | 卡区间 | — |
| max 设了 & min 空/0 & **disliked** | `lower` | 上限越低越好 | ← 从 equal 变成 lower |

**和 tiebreaker 的关键区别**：tiebreaker 是"先按 score 排，同分才看 resultPriority"；支配过滤**完全不看 score**，而是逐维度 pairwise —— 两件装备每个维度都要比一遍，只要 A 在**所有**维度上 ≥ B 且至少一个严格 >，B 就淘汰。resultDislike 改变的是每个维度"多少才算 ≥"。

**例子**：速度鞋，resultDislike 包含 `spd`，没设速度上限

| 模式 | 含义 | 速度鞋比较口径 |
|---|---|---|
| `higher`（默认，不 disliked） | 速度高的"好" | `(A.spd > B.spd) → A 在速度维支配 B` |
| `lower`（disliked + 没设上限） | 速度低的"好" | `(A.spd < B.spd) → A 在速度维支配 B` |
| `equal`（disliked + 设了 min > 0） | 刚好等于下限"最好" | 偏离 min 越远越差 |

### 阶段 ③：后端 Top-K 保留 + 结果排序

**时机**：穷举 6 件组合、计算完整结果行、过属性上下限约束之后。

**位置**：`TopKResultCollector.java` + `ResultPriorityComparator.java`

**介入方式**：**主力排序 key**，覆盖全部 17 个字段（`resultPriority.js` 里的 `RESULT_PRIORITY_FIELDS`），包括前端算不出来的派生属性：

```java
// ResultPriorityComparator.valueOf —— switch 映射全字段
case "atk":    return stats.getAtk();
case "ehp":    return stats.getEhp();    // 派生：HP × (1 + DEF/200)
case "dmg":    return stats.getDmg();    // 派生：单技能伤害估算
case "mcdmg":  return stats.getMcdmg();  // 派生：暴击伤害
case "dmgh":   return stats.getDmgh();   // 派生：持伤
case "dmgd":   return stats.getDmgd();   // 派生：防御贡献伤害
case "s1":     return stats.getS1();     // S1 专属装备件数
case "score":  return stats.getScore();  // solver 里的综合评分
case "bs":     return stats.getBs();     // build score
case "priority": return stats.getPriority();
```

**为什么这阶段能用派生属性而前端不行**：TopKResultCollector 接收的 `HeroStats` 已经是完整结果行 —— solver 已经对 6 件装备算完了英雄属性、EHP、DMG、S1~S3 件数这些。前端候选阶段只看单件装备，没有完整英雄上下文。

Top-K 保留器的 comparator：

```java
// TopKResultCollector.java:L54
// heap 里最小的"最差结果"在 head，新结果更好就顶掉它
public synchronized void offer(final HeroStats result) {
    if (heap.size() < capacity) { heap.offer(result); return; }
    if (bestFirstComparator.compare(result, heap.peek()) < 0) { // result 更好
        heap.poll();
        heap.offer(result);
    }
}
```

bestFirstComparator（就是 ResultPriorityComparator）：

```java
// ResultPriorityComparator.compare
public int compare(final HeroStats left, final HeroStats right) {
    for (final String field : orderedFields) {        // ← 按 resultPriority 顺序
        final int cmp = dislikedFields.contains(field)
                ? Integer.compare(valueOf(right, field), valueOf(left, field))  // disliked → 反序（越低越好）
                : Integer.compare(valueOf(left, field), valueOf(right, field)); // 正常 → 正序（越高越好）
        if (cmp != 0) return -cmp;                    // 不等直接出结果
    }
    // resultPriority 全比完都相等 → 用这些兜底
    if (left.priority != right.priority) return -cmp(priority);
    if (left.bs       != right.bs)       return -cmp(bs);
    if (left.score    != right.score)    return -cmp(score);
    return -cmp(dmg);
}
```

Top-K 的容量是 `MAX_RETAINED_RESULTS = 500`。heap 先积累满 500 条，之后每来一条就跟 head（当前最差）比，resultPriority 判定更好就顶掉旧的。最终输出时再按 comparator 排序一遍得到 best-first 顺序。

### 三个阶段的介入方式汇总

| 阶段 | 比较对象 | 介入方式 | 影响范围 | resultPriority 覆盖字段 |
|---|---|---|---|---|
| PriorityFilter tiebreaker | 单件装备的 score + 同部位同套装其它单件 | **只在 score 相同**时，按**属性优先级滑块权重降序分桶比**（同权重属性合并求和）→ disliked 兜底 | 候选装备数量（Top K 过滤） | 8 基础属性（atk/hp/def/spd/cr/cd/eff/res），用**滑块值**而非 resultPriority 顺序 |
| DominanceFilter 比较方向 | 单件装备 vs 同组内其它单件的逐维度支配关系 | **只看 resultDislike** 改变比较方向（higher/lower/equal/ignored） | 候选装备数量（淘汰被支配装备） | 8 基础属性（和上下限一起决定） |
| TopKResultCollector | **完整结果行**（6 件装备 × 算完属性 × 派生属性都有） | **主力排序**：resultPriority 顺序逐字段比，disliked 反序 | Top-K 留哪 K 条 + 最终展示顺序 | 17 字段全覆盖（8 基础 + ehp/dmg/mcdmg/dmgh/dmgd/s1~s3/score/bs/priority） |
