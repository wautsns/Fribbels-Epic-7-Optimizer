# 配装器（optimizer）自检脚本

不依赖 Electron / Jest 的纯 Node 脚本，**不会被 `yarn test`(jest) 收集**，需要手动跑。

```bash
# 仓库根目录执行，输出 ALL PASS
node test/optimizer/priority-filter-check.js
```

| 脚本 | 覆盖内容 |
|---|---|
| `priority-filter-check.js` | 「属性优先级过滤（Top %）」：滑块百分比**原样生效**、**选中的套装各自取 Top%（至少 3 件）、其它套装整体取 Top%**、**同分按结果优先级 / 未加权 roll / id 取舍**、`Top 100%` 时原样返回 |

## 现在的规则（`app/js/lib/priorityFilter.js`）

1. 候选装备先按滑块加权分数（8 个属性优先级）打分；
2. **滑块上的 Top% 原样生效**（不会被自动下调）；界面默认 **4%**、上限 **13%**（步长 3 → 1/4/7/10/13）；
3. 按部位处理候选：
   - 用户**选中**的套装（4+2 / 2+2+2 / 只选 4 / 只选 2 / 2+2 里的那些）→ **每个套装各自**取前
     `Top%`，件数下限 **3 件**；
   - **其它**套装 → 把它们**当成一个整体**排序后一起取前 `Top%`（某个套装整体很弱时不会硬塞，
     只有当它的装备能排进「其它套装」前 Top% 才保留）；
4. **同分时的先后**：按结果优先级（`resultPriority` 依次比较，`resultDislike` 里的字段反向）
   → 未加权 roll 总和 → `id` 升序。也就是说同分块里留下的是“对目标更好的那批”，
   而且结果可复现（不会因为装备列表顺序变化而变）。

运行时 `console` 会打印每个部位最终保留多少件、用了哪个百分比、估计组合数（超过 1e9 会提示“搜索会比较慢”），
方便排查“为什么没搜到某个解”或者“为什么这次搜得久”。

## 为什么需要这套规则

原来的实现是**逐部位**（不分套装）按 Top % 截断。以 `docs/ZQMT_GVG2.json` 里的利纳柯为例
（速度套 ×4 + 追击套 ×2，只给速度 8 分）：

- 42 双“速度主属性”的靴子分数**完全相同**（(0+45)/4×8 = 90），名额只有 25 双；
- 排序只看装备在数组里的顺序，3 双**追击套**速度靴排在第 40/41/42 位 → 全被切掉；
- 池子里只剩速度套靴子，于是“2 件追击套”只能拿**盔甲**去凑：速度套盔甲 22 速 → 追击套盔甲 17 速，**−5 速**；
- 结果：最高只能搜到 **310**，而实际最优解是 **315**（把攻击/命中各给 1 分打破平局才能搜到）。

改成「选中的套装各自按 Top% 保留（至少 3 件）+ 其它套装整体按 Top% 保留」之后，
310 → **315** 稳定成立，而且 4+2 场景下候选池比原来小很多（组合数 1.4e9 → 4.3e6）。

没有套装约束时（只选 4 件套 / 2+2 / 什么都没选），其它套装是**整体**再取 7%，所以每个部位大约是
「该部位 Top% + 选中套装的名额」的量级（Estelle 2+2：36/36/41/28/29/29 ≈ 1.25e9 组合），
既覆盖了「别的套装搭配可能更强」，又不会像“每个套装各留 1 件”那样把池子撑到 6.5e9。
