# 配装器（optimizer）自检脚本

不依赖 Electron / Jest 的纯 Node 脚本，**不会被 `yarn test`(jest) 收集**，需要手动跑。

```bash
# 仓库根目录执行，输出 ALL PASS
node test/optimizer/priority-filter-check.js
```

| 脚本 | 覆盖内容 |
|---|---|
| `priority-filter-check.js` | 「属性优先级过滤（Top %）」：滑块百分比**原样生效**、每个 (部位 × 套装) 组的名额 = max(下限, ceil(Top% × 组内件数))、选中套装至少 3 件 / 未选中至少 1 件、不足部位 Top% 时再补足、**同分按结果优先级 / 未加权 roll / id 取舍**、`Top 100%` 时原样返回 |

## 现在的规则（`app/js/lib/priorityFilter.js`）

1. 候选装备先按滑块加权分数（8 个属性优先级）打分；
2. **滑块上的 Top% 原样生效**（不会被自动下调）；
3. 每个 **(部位 × 套装)** 组的名额 = `max(下限, ceil(Top% × 该组在全量里的件数))`，下限：
   - 用户**选中**的套装（4+2 / 2+2+2 / 只选 4 / 只选 2 / 2+2 里的那些）→ 至少 **3 件**；
   - **其它**套装 → 至少 **1 件**（套装效果可能更强，不能整体淘汰）；
4. 这些加起来还不够该部位的 `Top%` 时，再从该部位全套装里按排序补足到 Top%
   （各套装名额之和本来就不低于部位 Top%，所以这一步基本只是兜底）；
5. **同分时的先后**：按结果优先级（`resultPriority` 依次比较，`resultDislike` 里的字段反向）
   → 未加权 roll 总和 → `id` 升序。也就是说同分块里留下的是“对目标更好的那批”，
   而且结果可复现（不会因为装备列表顺序变化而变）。

运行时 `console` 会打印每个部位最终保留多少件、用了哪个百分比、估计组合数（超过 1e9 会提示“搜索会比较慢”），
方便排查“为什么没搜到某个解”或者“为什么这次搜得久”。

## 为什么需要这套规则

原来的实现是**逐部位**（不分套装）按 Top % 截断。以 `docs/ZQMT_GVG2.json` 里的利纳柯为例
（速度套 ×4 + 追击套 ×2，只给速度 8 分）：

- 42 双“速度主属性”的靴子分数**完全相同**（(0+45)/4×8 = 90），名额只有 25 双；
- 排序只看装备在数组里的顺序，3 双**追击套**速度靴排在第 40/41/42 位 → 全被切掉；
- 池子里只剩速度套靴子，于是“2 件追击套”只能拿**盔甲**去凑：速度套盔甲 22 速 → 追击套盔甲 17 速，**−5 速**；
- 结果：最高只能搜到 **310**，而实际最优解是 **315**（把攻击/命中各给 1 分打破平局才能搜到）。

改成「每个套装按自己的 Top% 保留（选中套装至少 3 件、其它至少 1 件）+ 不足部位 Top% 再补足」之后，
310 → **315** 稳定成立，而且每个套装的名额按该套装自己的件数算，4+2 场景下候选池比原来小很多
（组合数 1.4e9 → 4.3e6）。

没有套装约束时（只选 4 件套 / 2+2 / 什么都没选），每个套装在每个部位都留代表，池子大约 20 多件/部位：
既覆盖了「某套装 ×4/×2 的加成可能更强」，又不会把搜索拖慢。注意这时 **7% 往往放不进预算**
（全套装 × 7% ≈ 6.5e9 组合），会自动降到 1%/3%，日志里会写实际生效的百分比。
